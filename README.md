# CampusIncident

CampusIncident is a Flutter app that helps ALU students report campus problems, like a broken chair, a water shortage or a power outage, and follow each report until it is fixed. Campus staff get a dashboard to review reports, update their status and keep students informed.

- **Demo video:** []
- **Download the Android app:** [latest release](https://github.com/ishejaladouce/campus-incident-app/releases/latest) (`app-release.apk`)

## Why this app

Campus issues are often reported by word of mouth or in group chats, so reports get lost and students rarely hear what happened next. CampusIncident gives everyone one place to report a problem, and a clear status timeline that shows who did what and when.

## Features

**For students**
- Sign up with an ALU email (`@alustudent.com` or `@alueducation.com`) and verify it before using the app
- Report an issue with a category, title, location, description, priority and an optional photo from the camera or gallery
- Browse all reports, search by title, description or location, and filter by category and status
- Open a report to see its photo, the staff note and the full status timeline
- Follow their own reports in **My reports**
- Get notified in the app when staff update or remove one of their reports
- Delete their own report while it is still *Submitted*

**For staff**
- A dashboard with counts by status, new reports sorted by priority and then by age, and an alert for open high-priority reports
- Update a report's status (*Submitted*, *In progress*, *Resolved*, *Rejected*) with a note for the student; rejecting requires a reason
- Remove spam, duplicate or inappropriate reports

**Built with care**
- Live form validation with regular expressions, character counters and clear error messages
- Friendly messages for network and server errors, timeouts, and a *Try again* button when loading fails
- Responsive layout for small phones, large phones, tablets, landscape and large text
- Access rules enforced on the server with Firestore security rules, not just hidden in the UI

## Tech stack

| Area | What I used |
| --- | --- |
| Framework | Flutter (Dart), Material 3 |
| State management | Provider (`ChangeNotifier`) |
| Authentication | Firebase Authentication (email and password, email verification) |
| Database | Cloud Firestore, with real-time streams |
| Photo storage | Supabase Storage |
| Photos | `image_picker` (camera and gallery, compressed before upload) |

**A note on photo storage.** The assignment asks for Firebase Storage. New Firebase projects need the paid Blaze plan for Storage, and activating it required a prepayment I could not make. So photo storage sits behind one interface, `ImageStorageService`, with two versions:
- `SupabaseImageStorage`, which the app uses now
- `FirebaseImageStorage`, which is written and ready

Switching back to Firebase Storage is a one-line change in `lib/main.dart`.

## How the code is organized

Screens never talk to Firebase or Supabase directly. Each layer only uses the one below it:

```
Screens and widgets  ->  Providers (app state)  ->  Services (data access)  ->  Firebase and Supabase
```

### State management

The app uses **Provider**. Three providers are registered once in `main.dart` and shared by every screen:

| Provider | What it holds |
| --- | --- |
| `AuthProvider` | The logged-in user, their profile and role, loading and errors |
| `IncidentProvider` | Live reports from Firestore, search text, filters, dashboard lists, loading and errors |
| `NotificationProvider` | A student's notifications and unread count |

When staff change a status, Firestore pushes the change to every device that is listening. The provider updates its list and the screens rebuild on their own, with no refresh needed. `setState` is only used for small things that belong to one screen, like showing a password or the photo picked in the form.

## Data model (Cloud Firestore)

| Collection | Main fields |
| --- | --- |
| `users/{uid}` | `name`, `email`, `role` (`student` or `staff`), `createdAt` |
| `incidents/{id}` | `title`, `category`, `description`, `location`, `priority`, `imageUrl`, `status`, `reportedBy`, `reporterName`, `staffNote`, `history`, `createdAt`, `updatedAt` |
| `notifications/{id}` | `userId`, `incidentId`, `incidentTitle`, `type`, `status`, `message`, `read`, `createdAt` |

Photos are stored in the Supabase bucket `incident-images` as `{incidentId}.jpg`, and each incident keeps only the photo's link.

## Roles and security

- Everyone who signs up is a **student**. Users can never change their own role.
- **Staff** accounts are created by an administrator with the Firebase Admin SDK (see below).
- The rules in [`firestore.rules`](firestore.rules) make sure that:
  - only verified ALU accounts can read or create reports
  - students can only create reports as themselves
  - only staff can change a status, and only the status fields
  - students can only delete their own report while it is still *Submitted*
  - each student can only read their own notifications
- Other students see "A student" instead of the reporter's name.

## Getting started

### What you need
- Flutter (stable channel) and Android Studio, with an emulator or an Android phone
- A Firebase project with **Email/Password** sign-in and **Cloud Firestore** turned on
- A Supabase project with a **public** bucket called `incident-images`

### 1. Get the code
```bash
git clone https://github.com/ishejaladouce/campus-incident-app.git
cd campus-incident-app
flutter pub get
```

### 2. Connect Firebase
`lib/firebase_options.dart` already points to this project's Firebase app. To use your own Firebase project:
```bash
dart pub global activate flutterfire_cli
flutterfire configure --platforms=android
```
Then paste the contents of `firestore.rules` into **Firebase Console > Firestore Database > Rules** and click **Publish**.

### 3. Connect Supabase
Put your project URL and **publishable (anon) key** in `lib/config/supabase_config.dart`. These are meant to be public. Never put the secret or `service_role` key in the app.

Then allow the app to upload and view photos, in the Supabase **SQL Editor**:
```sql
create policy "App can upload incident images"
on storage.objects for insert
to anon, authenticated
with check (bucket_id = 'incident-images');

create policy "App can view incident images"
on storage.objects for select
to anon, authenticated
using (bucket_id = 'incident-images');
```

### 4. Run the app
```bash
flutter run
```

### 5. Run the tests
```bash
flutter test
```
The tests in `test/widget_test.dart` check the ALU email regular expression and every form rule: email, name, passwords and text lengths.

### 6. Build the APK
```bash
flutter build apk --release
```
The file is saved to `build/app/outputs/flutter-apk/app-release.apk`.

## Installing the APK on a phone

1. Download `app-release.apk` from the [latest release](https://github.com/ishejaladouce/campus-incident-app/releases/latest).
2. Open it and allow **Install unknown apps** when Android asks. On Samsung phones, you may need to turn off Auto Blocker for a moment.
3. Tap **Install** and open **CampusIncident**. The app needs an internet connection.

## Accounts for testing

- **Student:** sign up in the app with any ALU email and click the link in the verification email.
- **Staff:** a demo staff account is shared in the technical report.

### Creating a staff account

Staff accounts are created by an administrator, outside the app, with a small Node.js script that uses the Firebase Admin SDK. The script creates a verified login and a Firestore profile with `role: "staff"`. It needs a private service-account key from **Firebase Console > Project settings > Service accounts**. That key gives full access to the project, so it is never committed to this repository and should be deleted after use.

## Known limitations

- Photos are in a public bucket, protected by unguessable file names. A production version would use a private bucket with signed links.
- When a report is deleted, its photo stays in storage, because the storage policy deliberately blocks anonymous deletes.
- Notifications only appear inside the app; there are no push notifications yet.
- Free Supabase projects pause after about a week without activity and need to be restored from the Supabase dashboard.
